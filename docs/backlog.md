### CB-071: Peer-closed keep-alive connection surfaces as non-retryable `invalidResponse`; transport-neutral error taxonomy
**Priority**: Medium
**Description**: Audit 2026-09-18. When the daemon restarts or a NAT idles out the TCP session, the next request's send succeeds (kernel buffers) and receive gets a clean EOF; `HTTPReceive` calls `parser.finish()` with no framing, which throws `DockerAPIError.invalidResponse`. On the TLS path that is not in the retry set (`.connectionFailed/.networkTimeout/.tlsConnectionFailed`), `DockerAPIError+Retry` marks it non-transient, `_isConnected` stays true, and the user sees "Invalid response from Docker daemon — the daemon may be incompatible". (Before CB-066 the Unix path recovered only because it retried unconditionally; it now retries only when the send was never attempted or the request opts into a post-send replay, so a GET still recovers but the error taxonomy problem remains.) `receiveChunk` also drops `isComplete`. Related: after CB-053 the receive/parse errors are still all `.tlsConnectionFailed("…")`, so a local Unix-socket parse failure reads "TLS connection failed". Fix: map EOF-before-any-bytes to a transport error and mark the transport disconnected; add a transport-neutral error case (or inject an error mapper via `NWConnectionTransport.Config` like `mapSendFailure`); tests for EOF on a reused connection.

**Acceptance** (BA 2026-10-14) — Size **L**. Flag: **two branches** — (a) EOF on a reused connection becomes a transport error that marks the client disconnected and is retried (bug, size M); (b) transport-neutral error taxonomy, so Unix-socket failures stop reading "TLS connection failed", plus `receiveChunk` honouring `isComplete` (refactor, size M). Do (a) first; kept split (PM 2026-10-14). Flag: code-read; the user-visible symptom is on the TLS path, which the QA runtime does not cover, so (a) on TLS is proven by unit tests only. Design (architecture §13): new `DockerAPIError.connectionClosed` (peer EOF before any response byte; transient; marks the transport disconnected) and `.transportFailed(String)` for non-TLS receive/parse failures, mapped through the injected error mapper on `NWConnectionTransport.Config`; transient copy "Lost connection to <runtime>. Reconnecting…".
- (a) Given a connection that served one request and whose peer then closed it, when the next GET is sent and receive returns EOF before any byte, then the client maps it to a transport error, marks itself disconnected, reconnects, and the GET succeeds without an error shown to the user (tests on both the Unix and TLS transports).
- (a) Failure path: given the daemon is down so the reconnect is refused, when the retry runs, then the user sees the connection-failed or runtime-not-running message, never "Invalid response from Docker daemon — the daemon may be incompatible".
- (b) Given a malformed HTTP response on the Unix-socket path, when it is parsed, then the error text does not mention TLS; given the same on the TLS path, then the text names the transport neutrally.
- QA check (Mini, TC-CB-16; TC-CB-09 is the daily regression signal): with the dashboard connected to `QA Runtime`, run `ssh cbqa-ctl api-stop`, wait two refresh intervals, then `ssh cbqa-ctl api-start`; within two refresh intervals the six `cbqa-` containers are back without relaunching ContainerBar, and no banner or message read during the outage contains "Invalid response" or "TLS connection failed" (capture each verbatim).

### CB-073: Replace the 100 ms `withObservationTracking` polling loop in `StatusItemController` with event-driven observation
**Priority**: Medium
**Description**: Audit 2026-09-18; narrowed 2026-09-22 — the `ContainerStore.startSettingsObservation` half was replaced in PR #58 (CB-065) by a synchronous observer registry on `SettingsStore`, so only the `StatusItemController` icon loop remains. Originally: `StatusItemController` (icon updates) and `ContainerStore.startSettingsObservation` both loop `withObservationTracking { … } onChange: { Task { … } }` followed by `Task.sleep(100 ms)`. `onChange` is one-shot: after it fires, nothing is tracked until the next iteration re-registers, so changes landing during the sleep are missed. Scenario (local socket, refresh < 100 ms): `isRefreshing = true` fires -> icon draws the refresh arrow; `containers`/`isRefreshing = false` land 40 ms later with no tracker registered; the icon sits on the refresh glyph until the next timer tick and the container count lags one interval.
