# ContainerBar Backlog

Prioritized list of planned features, improvements, and technical debt for ContainerBar - macOS menu bar Docker/Podman monitoring app.

Item ids are stable `CB-NNN` numbers and are never reused. Completed items move to [`docs/resolved.md`](resolved.md).

## High Priority

### CB-064: `ContainerStore.refresh` has no cancellation or generation fencing; host switch lets stale responses overwrite the new host
**Priority**: High
**Description**: Audit 2026-09-18. `refresh()` copies `fetcher` into a local before awaiting and writes `containers`/`stats`/`isConnected`/`metricsHistory` unconditionally after the `await`. `reinitializeFetcher()` clears state, forces `isRefreshing = false`, and callers then start `refresh(force: true)`, so two fetches overlap. Scenario: timer refresh in flight against a slow SSH host, user switches to Local Docker; local returns first, then the SSH response arrives and overwrites the store with the remote host's containers while the header says "Local Docker". The first refresh's `defer { isRefreshing = false }` also fires while the second is still running, so the icon flips to idle early. `performContainerAction` -> `refresh(force: true)` plus the router's `reopenMenu` -> `menuWillOpen` -> `refresh()` produces the same overlap on every start/stop/restart. Fix: hold the running refresh in a `Task` property, cancel it in `reinitializeFetcher()`, stamp each refresh with a generation counter checked after every `await` before writing state, and replace `force` with cancel-and-restart. Tests: host switch mid-fetch must not apply the stale result.

### CB-065: Host lifecycle mutations bypass the store: removing or editing the active host never reinitializes the fetcher
**Priority**: High
**Description**: Audit 2026-09-18. Host-switch orchestration is duplicated in `StatusItemController+MenuBuilding.swift` (`onHostChanged` -> `reinitializeFetcher()` + `refresh(force:)`) and `ConnectionSettingsPane.setDefaultHost` (reinitialize, no refresh — in manual-refresh mode the store stays empty until the menu opens). `ConnectionSettingsPane.removeSelectedHost` calls `settings.removeHost(id:)`, which nulls `selectedHostId` so `selectedHost` silently falls back to the default host, but nothing reinitializes: `ContainerStore.startSettingsObservation` tracks only `settings.refreshInterval`, so the store keeps polling the deleted host's SSH tunnel while the dashboard header names the fallback host. `SettingsStore.updateHost(_:)` for the currently selected host (changed SSH user/port/socket) persists but the live client keeps the old config until a switch or relaunch. Fix: move orchestration into a single `ContainerStore.switchHost()` and have the store observe `settings.selectedHostId` and `settings.hosts` (config of the selected host), so every mutation path — menu switch, Settings default, remove, edit, hunt-mode seed — converges. Pair with CB-064 so the switch cancels in-flight work. Tests for remove-active-host and edit-active-host.

## Medium Priority

### CB-066: Unix-socket/SSH request path retries non-idempotent requests; TLS path guards on `isIdempotent`, Unix path does not
**Priority**: Medium
**Description**: Audit 2026-09-18. `DockerAPIClientImpl+UnixSocket.performRequest` catches any non-cancellation error, optionally closes/reconnects, then unconditionally issues the request a second time. `DockerAPIClientImpl+TLS` has `guard request.isIdempotent else { throw error }` (commit `6e80882`); `HTTPRequest.isIdempotent` has no other reference. Scenario: `POST /containers/x/restart` reaches the daemon, the socket or tunnel drops before the response, the retry fires and the container restarts twice (or `stop?t=` is re-issued). It also retries on parse errors. Fix: apply the same `isIdempotent` guard before the second attempt on the Unix path, and add tests for both paths (idempotent GET retried, POST not).

### CB-067: SSH tunnel robustness: stderr pipe never drained, and `reconnect()` is not single-flight
**Priority**: Medium
**Description**: Audit 2026-09-18. (1) `SSHTunnelProcessLauncher` attaches an `errorPipe` to `ssh`'s stderr and reads it only in `parseLaunchError` when the process died within the 1 s launch check; after adoption nobody reads it. With a wrong `remoteSocketPath` or a down remote daemon, every forwarded connection makes ssh print `channel N: open failed…`; after ~700 lines the 64 KB pipe fills, ssh blocks on `write(2)`, the tunnel stops forwarding, `isRunning` stays true so `hasDied` never trips, and (with CB-062) every request hangs. Fix: after `waitForSocket` succeeds, install a `readabilityHandler` that logs/discards (cleared in `disconnectTunnelState`), or redirect stderr to `FileHandle.nullDevice` post-adoption. (2) `SSHTunnelConnection.reconnect()` calls `getOrCreateConnectTask(forceReconnect: true)`, bypassing task reuse; `ContainerFetcher.fetchStatsForContainers` issues up to 10 concurrent requests that each call `reconnect()` on `hasDied`, so N ssh processes launch, N-1 are terminated, and the losers throw a bare `CancellationError` (not a `DockerAPIError`, so `withRetry` won't retry and the store shows it as a connection error). Fix: coalesce `reconnect()` behind an in-flight task like `TLSConnectCoordinator.reconnect`, and throw a `DockerAPIError` for superseded attempts. Tests for both.

### CB-068: Stats are silently truncated to the first 10 running containers
**Priority**: Medium
**Description**: Audit 2026-09-18. `ContainerFetcher.maxConcurrentStatsFetches = 10` is applied as `runningContainers.prefix(10)` — a count cap, not a concurrency bound. Containers 11+ never get stats, `buildMetricsSnapshot` sums only the fetched ones, and `ContainerFetcherTests.largeContainerCountFetch` ("20 running … mimics Beelink host") enshrines it with `#expect(result.stats.count <= 10)`. On the Beelink host cards 11+ show no CPU/MEM and the status-item percentage is wrong, with which ten get stats depending on Docker's list order. (Concurrency is largely nominal anyway: every request serializes on the transport's `ioGate`.) Fix: bound concurrency (chunked `withTaskGroup` batches or a limiter) but fetch stats for all running containers; update the test to assert `stats.count == 20`.

### CB-069: Aggregate memory limit sums per-container limits, so unconstrained containers inflate the denominator
**Priority**: Medium
**Description**: Audit 2026-09-18. `ContainerFetcher.buildMetricsSnapshot` computes `totalMemLimit = statsList.reduce(0) { $0 + $1.memoryLimitBytes }`. Docker reports `memory_stats.limit` = host `MemTotal` for containers with no cgroup limit (the common case), so three unlimited containers on a 16 GB host render "/ 48 GB" in `GeneralStatsGrid`, the memory fraction in `StatusItemController.updateIcon` is one-third of reality, and `ContainerMetricsSnapshot.overallHealth`'s 95 % warning can never trip. Fix: use `DockerSystemInfo.memoryTotal` (already decoded from `/info`) as the denominator, or `min(sum, hostTotal)`; at minimum de-duplicate limits equal to host memory. Test with a fixture of unlimited containers.

### CB-070: Multiplexed log-stream frame headers leak into the returned log text
**Priority**: Medium
**Description**: Audit 2026-09-18. `DockerAPIClientImpl.getContainerLogs` tries `String(data:encoding:.utf8)` first and only falls back to `parseMultiplexedLogs` when that fails. Non-TTY containers (the default) return 8-byte frame headers `[1|2, 0,0,0, size(4 BE)]` which are valid UTF-8 for virtually every real log, so the headers are embedded in the string that `LogViewerWindow` renders verbatim. The fallback only runs when a size byte happens to form an invalid sequence. `parseMultiplexedLogs` has no test, and its zero-length-frame `break` in `+ResponseHandling.swift` should be `continue`. Fix: decide framing from the container's `Config.Tty` (or probe the first 8 bytes: type in {0,1,2} and bytes 1–3 zero) and demultiplex first; add tests with a captured multiplexed payload.

### CB-071: Peer-closed keep-alive connection surfaces as non-retryable `invalidResponse`; transport-neutral error taxonomy
**Priority**: Medium
**Description**: Audit 2026-09-18. When the daemon restarts or a NAT idles out the TCP session, the next request's send succeeds (kernel buffers) and receive gets a clean EOF; `HTTPReceive` calls `parser.finish()` with no framing, which throws `DockerAPIError.invalidResponse`. On the TLS path that is not in the retry set (`.connectionFailed/.networkTimeout/.tlsConnectionFailed`), `DockerAPIError+Retry` marks it non-transient, `_isConnected` stays true, and the user sees "Invalid response from Docker daemon — the daemon may be incompatible". (The Unix path recovers only because it retries unconditionally, CB-066.) `receiveChunk` also drops `isComplete`. Related: after CB-053 the receive/parse errors are still all `.tlsConnectionFailed("…")`, so a local Unix-socket parse failure reads "TLS connection failed". Fix: map EOF-before-any-bytes to a transport error and mark the transport disconnected; add a transport-neutral error case (or inject an error mapper via `NWConnectionTransport.Config` like `mapSendFailure`); tests for EOF on a reused connection.

### CB-072: SSH argv injection: a user or host value beginning with `-` becomes an `ssh` option
**Priority**: Medium
**Description**: Audit 2026-09-18. `SSHTunnelProcessLauncher` builds `["ssh", …, "-p", port, "-L", "\(local):\(remote)", "\(user)@\(host)"]`. `remoteSocketPath` is validated (`+SSH.swift`) but `sshUser`/`host` are only whitespace-trimmed in `RemoteHostDraftBuilder` and are persisted/decoded from settings unvalidated. `sshUser = "-oProxyCommand=touch /tmp/pwned"` yields argv `-oProxyCommand=touch /tmp/pwned@host`, parsed by ssh as an option — arbitrary command execution via a crafted host entry (local-only, but a code-execution path through persisted config). Fix: pass the user with `-l <user>`, terminate options with `--` before the host, and reject `user`/`host` values starting with `-` in both `RemoteHostDraftBuilder` and `DockerAPIClientImpl.init`; add an argv-construction test.

### CB-073: Replace the 100 ms `withObservationTracking` polling loops with event-driven observation
**Priority**: Medium
**Description**: Audit 2026-09-18. `StatusItemController` (icon updates) and `ContainerStore.startSettingsObservation` both loop `withObservationTracking { … } onChange: { Task { … } }` followed by `Task.sleep(100 ms)`. `onChange` is one-shot: after it fires, nothing is tracked until the next iteration re-registers, so changes landing during the sleep are missed. Scenario (local socket, refresh < 100 ms): `isRefreshing = true` fires -> icon draws the refresh arrow; `containers`/`isRefreshing = false` land 40 ms later with no tracker registered; the icon sits on the refresh glyph until the next timer tick and the container count lags one interval. The two loops also wake the main actor 20x/s for the process lifetime in an idle menu-bar app. Fix: re-register inside `onChange` (continuation-driven loop) with a single coalesced pending update, or adopt `Observations` where the deployment target allows; test the icon-update cadence with an injected clock.

### CB-074: Sparkle updater starts in hunt mode via the Settings panes, and the DEBUG "Check for Updates" button is a silent no-op
**Priority**: Medium
**Description**: Audit 2026-09-18. `AppDelegate` skips `UpdaterController.shared` when `HuntMode.isActive`, but `GeneralSettingsPane` and `AboutPane` touch `UpdaterController.shared` directly, and `CONTAINERBAR_OPEN_SETTINGS_ON_LAUNCH=1` (used by the QA runner) opens Settings at launch — so the real `SPUStandardUpdaterController(startingUpdater: true)` starts on the Mac mini during hunts (scheduled feed checks, possible update prompt on the QA machine). In DEBUG `startingUpdater: false` means `checkForUpdates()` does nothing while the button stays enabled. `AppDelegate.updaterController` is redundant with the singleton. Fix: make updater construction explicit (injected, `nil` in hunt mode), and have the panes bind the button to `canCheckForUpdates`.

### CB-075: Settings persistence: any decode failure silently wipes saved hosts/sections, and `MatchType` raw values are UI strings
**Priority**: Medium
**Description**: Audit 2026-09-18. `SettingsStore.loadHosts` treats a missing blob and an undecodable blob identically (`try?`, logged at `.info` as "No saved hosts found"), then `if hosts.isEmpty { addHost(.local) }` -> `saveHosts()` overwrites the user's remote-host configuration. `DockerHost` has non-optional fields, so any future non-optional addition or a bad write loses every SSH/TLS host on next launch; `SettingsStoreHostSectionTests` enshrines "Decode fails silently". `loadSections` has the same drop-everything behaviour, and `ContainerSection.MatchType` persists its UI label as the Codable raw value (`"Container name contains"`), so any copy edit breaks decoding of all saved sections; `.labelEquals` with an empty value can never match because `split` omits empty subsequences. Fix: distinguish nil from decode error, log at `.error`, copy the raw blob to a `.backup` key before seeding defaults, decode tolerantly (`decodeIfPresent` with defaults) behind a schema-version key, give `MatchType` machine raw values with a separate `displayName` and a one-time migration. Tests for each.

### CB-076: Status-item menu lifecycle: open-state tracking, modal ordering, screen selection, duplicate size clamp
**Priority**: Medium
**Description**: Audit 2026-09-18. (1) `StatusItemController.toggleMenu` decides "open" by `menu.highlightedItem != nil`; the menu holds one custom-view item and the hotkey is keyboard-driven, so the pointer is rarely over it and the close branch cannot fire — the hotkey re-clicks the pressed status button instead. The delegate implements only `menuWillOpen`; add `menuDidClose(_:)` and an `isMenuOpen` flag. (2) `.remove` runs `NSAlert.runModal()` from inside the menu's tracking session while `.viewLogs` calls `closeMenuIfOpen()` first; close the menu before the modal. (3) `+MenuBuilding` clamps to `NSScreen.main` (the key-window screen, not the status item's) and re-applies a 300/400 clamp that `AutoResizingHostingView` (CB-054) already applies from `intrinsicContentSize`, so the two can disagree; use `statusItem.button?.window?.screen` and expose `minHeight`/`width` from the hosting view. (4) `rebuildMenu()` is only called inside the `Task` spawned from `nonisolated menuWillOpen`; verify on the mini whether the menu is empty on first show and consider `MainActor.assumeIsolated` for a synchronous rebuild. Also `ContainerGroupView.isExpanded` resets every open because the whole view tree is rebuilt — persist collapsed groups in the store if that is unwanted.

### CB-077: Error surfacing: fetcher-init error replaced by "not configured", and a second action on a busy container is dropped silently
**Priority**: Medium
**Description**: Audit 2026-09-18. `ContainerStore.initializeFetcher` catches `DockerAPIClientImpl.init`'s `socketNotFound` (Docker Desktop not running — the common launch case) into `connectionError`, but `refresh()` then overwrites it with "Docker connection not configured", so the mapped "Docker not running. Please start Docker Desktop." (`ConnectionErrorMessage`) is never shown and the user is told to check configuration. `performContainerAction` never retries `initializeFetcher()`, so actions fail with "not configured" even after Docker starts, until the next refresh. Separately, `ContainerStore+Actions` `guard !actionInProgress.contains(id) else { return }` drops a second action (Stop then Start) with no `lastActionError` while `ContainerActionRouter` still logs it and reopens the menu; nothing tests the debounce. Fix: have `initializeFetcher()` return its error and route it through `userFriendlyConnectionErrorMessage` on both paths; set a "busy" state on the dropped path and skip `onMenuReopenRequested` when the id is in progress. Tests for both.

### CB-078: Dashboard "Add Remote Host" form has drifted from `AddHostSheet`: Docker-only, no remote socket path
**Priority**: Medium
**Description**: Audit 2026-09-18. `HostPanelView.addHostForm` calls `RemoteHostDraftBuilder.build(nameInput:hostInput:userInput:portInput:)` without `runtime:`/`socketPath:`, so every host added from the dashboard is `runtime: .docker` with Docker's remote socket path; the form has no runtime picker or socket field, while `Settings/AddHostSheet` has both. A Podman host added from the dashboard fails to connect and, because hosts are not editable, must be deleted and re-added via Settings. CB-013's resolved note that the panel form is "the only add-host path" is stale. The form is also discarded silently when the panel closes or the Logs toggle sets `isHostPanelOpen = false`. Fix: extract one shared `RemoteHostFormFields` view (name/host/user/port/runtime/socket) driven by a common draft, used by both entry points — or drop the dashboard form and route "Add Remote Host" to the Settings sheet.

### CB-079: Port rendering breaks on Docker dual-stack bindings: duplicate `ForEach` ids and doubled port pills
**Priority**: Medium
**Description**: Audit 2026-09-18. Docker with IPv6 enabled returns one `PortMapping` per address family for the same private port (`0.0.0.0:8080->80/tcp` and `[::]:8080->80/tcp`), and tcp+udp on one port also share `privatePort`. `ContainerDetailPopover` uses `ForEach(container.ports.prefix(5), id: \.privatePort)` (duplicate ids: SwiftUI logs "ID occurs multiple times" and row rendering is undefined), and `ContainerCardView.formattedPorts` builds `publicPorts` via `compactMap` without de-duplication, so one published port shows as `:8080 :8080` or `:8080 +3`. Fix: key popover rows on a composite (`ip-privatePort-type`), de-duplicate `publicPorts` (ordered set) before formatting, lift `formattedPorts` into a pure helper, and unit-test it with a dual-stack fixture.

### CB-080: Connection-test result in `ConnectionSettingsPane` is not scoped to the host it ran against
**Priority**: Medium
**Description**: Audit 2026-09-18. `testResult`/`isTestingConnection` are pane-level `@State`, passed into `HostDetailsView` for whichever host is selected, and neither resets when `selectedHostId` changes (`testConnection` clears only when a new test starts). Fold into the CB-065 branch if convenient.

### CB-086: Release pipeline: `generate-appcast.sh` accepts a missing/mismatched VERSION, and `validate-release.py` cannot run from a clean checkout
**Priority**: Medium
**Description**: Audit 2026-09-18. `generate-appcast.sh` takes `VERSION="${1:-}"`; with no arg it exits 0 after writing enclosures of bare `ContainerBar.zip` (Sparkle resolves that relative to the feed -> 404 for every installed client once pushed to `docs/`), and a mistyped arg produces a URL for a tag that never exists. `build-release.sh` already reads the version from `Distribution/Info.plist`; this script reads nothing. Fix: default VERSION from PlistBuddy, `exit 1` on mismatch, refuse to run without a download prefix. Separately, `validate-release.py` hard-fails five local-`dist/` checks (`check_codesign`, `check_framework_rpath`, `check_required_resource_bundles`, `check_no_swiftpm_release_resource_path`, `check_notarization`) with `check(..., False, ...)` when `dist/` is absent, and `check_git_tag` checks only local tags — so running it from the mini or any clean checkout, exactly the posture RELEASING.md prescribes, yields 5+ spurious FAILs. The same properties are already verified on the uploaded zip in `check_gatekeeper_zip`. Fix: convert the local-dist checks to `skip()` (or delete them), check the tag via `git ls-remote --tags origin`. The 1398-line validator and its 1433-line test file should also split into artifact/appcast/cask modules.

### CB-093: Core minor correctness: `getContainer` cannot decode a real inspect payload, CPU% fallback ignores `percpu_usage`, cert loader passphrase lifetime
