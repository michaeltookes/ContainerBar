### CB-069: Aggregate memory limit sums per-container limits, so unconstrained containers inflate the denominator
**Priority**: Medium
**Description**: Audit 2026-09-18. `ContainerFetcher.buildMetricsSnapshot` computes `totalMemLimit = statsList.reduce(0) { $0 + $1.memoryLimitBytes }`. Docker reports `memory_stats.limit` = host `MemTotal` for containers with no cgroup limit (the common case), so three unlimited containers on a 16 GB host render "/ 48 GB" in `GeneralStatsGrid`, the memory fraction in `StatusItemController.updateIcon` is one-third of reality, and `ContainerMetricsSnapshot.overallHealth`'s 95 % warning can never trip. Fix: use `DockerSystemInfo.memoryTotal` (already decoded from `/info`) as the denominator, or `min(sum, hostTotal)`; at minimum de-duplicate limits equal to host memory. Test with a fixture of unlimited containers.

**Acceptance** (BA 2026-10-14) — Size **S**, one branch. Flag: found by code reading, not a repro; the `memory_stats.limit` = host total behaviour is Docker's documented one, Podman's is unverified until the QA check below runs.
- Given a stats fixture of three running containers with no memory limit, each reporting `memory_stats.limit` = 16 GiB, and `/info` `MemTotal` = 16 GiB, when `buildMetricsSnapshot` runs, then the memory denominator is 16 GiB (not 48), `GeneralStatsGrid` renders "/ 16 GB", and the status-icon memory fraction equals used ÷ 16 GiB.
- Given one container limited to 256 MiB plus two unlimited containers on a 16 GiB host, when the snapshot is built, then the denominator is 16 GiB, and given total usage at 95 % or more of it, `overallHealth` reports the warning state.
- Failure path: given `/info` failed or reported `MemTotal` = 0, when the snapshot is built, then the denominator falls back to the de-duplicated sum of limits, the tile still shows a unit, and no division by zero or crash occurs.
- QA check (Mini, QA runtime from CB-100): open the dashboard with the `cbqa-` fixture set running (three unlimited, one limited); the RAM tile's denominator equals the runtime's total memory (`podman info --format '{{.Host.MemTotal}}'`, same rounding as the tile, ±0.1 GB). Before the fix it reads about three times that, which is the repro.

### CB-070: Multiplexed log-stream frame headers leak into the returned log text
**Priority**: Medium
**Description**: Audit 2026-09-18. `DockerAPIClientImpl.getContainerLogs` tries `String(data:encoding:.utf8)` first and only falls back to `parseMultiplexedLogs` when that fails. Non-TTY containers (the default) return 8-byte frame headers `[1|2, 0,0,0, size(4 BE)]` which are valid UTF-8 for virtually every real log, so the headers are embedded in the string that `LogViewerWindow` renders verbatim. The fallback only runs when a size byte happens to form an invalid sequence. `parseMultiplexedLogs` has no test, and its zero-length-frame `break` in `+ResponseHandling.swift` should be `continue`. Fix: decide framing from the container's `Config.Tty` (or probe the first 8 bytes: type in {0,1,2} and bytes 1–3 zero) and demultiplex first; add tests with a captured multiplexed payload.

**Acceptance** (BA 2026-10-14) — Size **M**, one branch. Flag: partly a guess. A size byte of 0x80 or above makes the blob invalid UTF-8 and does trigger the demultiplexer, so whether headers leak depends on frame sizes ("virtually every real log" is overstated); the QA check below is the repro to capture first, and its payload becomes the test fixture.
- Given a captured non-TTY payload with stdout and stderr frames, including a zero-length frame mid-stream, when `getContainerLogs` returns, then the text equals the frame payloads concatenated in order with no header bytes, and the frames after the zero-length frame are kept (`continue`, not `break`).
- Given a TTY container (`Config.Tty = true`), when logs are fetched, then the raw stream is returned unchanged, even if its first 8 bytes look like a frame header.
- Failure path: given a payload whose last frame declares more bytes than remain, when it is parsed, then every complete frame is returned, the partial frame does not crash the parser, and the truncation is logged at debug level.
- QA check (Mini): open the logs panel and the log viewer for `cbqa-logs`; the text shows `cbqa-line-1`, `cbqa-line-2`, `cbqa-line-3`, `cbqa-err-1`, each line starting exactly with `cbqa-` (no box, control, or replacement character before it). Repeat with a temporary TTY container the brief creates and removes (`podman run -dt --name cbqa-tty …`).

### CB-071: Peer-closed keep-alive connection surfaces as non-retryable `invalidResponse`; transport-neutral error taxonomy
**Priority**: Medium
**Description**: Audit 2026-09-18. When the daemon restarts or a NAT idles out the TCP session, the next request's send succeeds (kernel buffers) and receive gets a clean EOF; `HTTPReceive` calls `parser.finish()` with no framing, which throws `DockerAPIError.invalidResponse`. On the TLS path that is not in the retry set (`.connectionFailed/.networkTimeout/.tlsConnectionFailed`), `DockerAPIError+Retry` marks it non-transient, `_isConnected` stays true, and the user sees "Invalid response from Docker daemon — the daemon may be incompatible". (Before CB-066 the Unix path recovered only because it retried unconditionally; it now retries only when the send was never attempted or the request opts into a post-send replay, so a GET still recovers but the error taxonomy problem remains.) `receiveChunk` also drops `isComplete`. Related: after CB-053 the receive/parse errors are still all `.tlsConnectionFailed("…")`, so a local Unix-socket parse failure reads "TLS connection failed". Fix: map EOF-before-any-bytes to a transport error and mark the transport disconnected; add a transport-neutral error case (or inject an error mapper via `NWConnectionTransport.Config` like `mapSendFailure`); tests for EOF on a reused connection.

**Acceptance** (BA 2026-10-14) — Size **L**. Flag: **two branches** — (a) EOF on a reused connection becomes a transport error that marks the client disconnected and is retried (bug, size M); (b) transport-neutral error taxonomy, so Unix-socket failures stop reading "TLS connection failed", plus `receiveChunk` honouring `isComplete` (refactor, size M). Do (a) first. Flag: code-read; the user-visible symptom is on the TLS path, which the QA runtime does not cover, so (a) on TLS is proven by unit tests only.
- (a) Given a connection that served one request and whose peer then closed it, when the next GET is sent and receive returns EOF before any byte, then the client maps it to a transport error, marks itself disconnected, reconnects, and the GET succeeds without an error shown to the user (tests on both the Unix and TLS transports).
- (a) Failure path: given the daemon is down so the reconnect is refused, when the retry runs, then the user sees the connection-failed or runtime-not-running message, never "Invalid response from Docker daemon — the daemon may be incompatible".
- (b) Given a malformed HTTP response on the Unix-socket path, when it is parsed, then the error text does not mention TLS; given the same on the TLS path, then the text names the transport neutrally.
- QA check (Mini): with the dashboard connected to the QA runtime, restart the runtime (`podman machine stop && podman machine start`); within two refresh intervals the five `cbqa-` containers are back without relaunching ContainerBar, and no banner or message read during the outage contains "Invalid response" or "TLS connection failed" (capture each verbatim).

### CB-072: SSH argv injection: a user or host value beginning with `-` becomes an `ssh` option
**Priority**: Medium
**Description**: Audit 2026-09-18. `SSHTunnelProcessLauncher` builds `["ssh", …, "-p", port, "-L", "\(local):\(remote)", "\(user)@\(host)"]`. `remoteSocketPath` is validated (`+SSH.swift`) but `sshUser`/`host` are only whitespace-trimmed in `RemoteHostDraftBuilder` and are persisted/decoded from settings unvalidated. `sshUser = "-oProxyCommand=touch /tmp/pwned"` yields argv `-oProxyCommand=touch /tmp/pwned@host`, parsed by ssh as an option — arbitrary command execution via a crafted host entry (local-only, but a code-execution path through persisted config). Fix: pass the user with `-l <user>`, terminate options with `--` before the host, and reject `user`/`host` values starting with `-` in both `RemoteHostDraftBuilder` and `DockerAPIClientImpl.init`; add an argv-construction test.

**Acceptance** (BA 2026-10-14) — Size **S**, one branch, concrete repro. BA recommendation for the PM: promote to High (a code-execution path through persisted config in a public app).
- Given an SSH host with user `alice`, host `qa.example.com`, port 22, when `SSHTunnelProcessLauncher` builds argv, then it contains `-l alice` and `-p 22`, the `-L` mapping, then `--`, and `qa.example.com` as the final argument, and no argument has the form `user@host` (argv-construction unit test).
- Failure path: given a user or host value starting with `-` (for example user `-oProxyCommand=touch /tmp/cbqa-pwned`), when the user saves it in `AddHostSheet` or the dashboard Add Remote Host form, then saving is refused with an inline message and nothing is persisted.
- Failure path: given such a value is already in saved settings (written by an older build), when `DockerAPIClientImpl.init` runs for that host, then it throws a validation error that the UI shows as a connection error, and no `ssh` process is launched.
- QA check (Mini, harmless payload): Settings > Connections > Add Host, type SSH, host `cbqa-invalid.invalid`, user `-oProxyCommand=touch /tmp/cbqa-pwned`; try to save, and if it saves, select it and press Test Connection. Pass: `test ! -e /tmp/cbqa-pwned` succeeds and the save was refused. On today's build the file appears, which is the repro. Remove the host and the file afterwards.

### CB-073: Replace the 100 ms `withObservationTracking` polling loop in `StatusItemController` with event-driven observation
**Priority**: Medium
**Description**: Audit 2026-09-18; narrowed 2026-09-22 — the `ContainerStore.startSettingsObservation` half was replaced in PR #58 (CB-065) by a synchronous observer registry on `SettingsStore`, so only the `StatusItemController` icon loop remains. Originally: `StatusItemController` (icon updates) and `ContainerStore.startSettingsObservation` both loop `withObservationTracking { … } onChange: { Task { … } }` followed by `Task.sleep(100 ms)`. `onChange` is one-shot: after it fires, nothing is tracked until the next iteration re-registers, so changes landing during the sleep are missed. Scenario (local socket, refresh < 100 ms): `isRefreshing = true` fires -> icon draws the refresh arrow; `containers`/`isRefreshing = false` land 40 ms later with no tracker registered; the icon sits on the refresh glyph until the next timer tick and the container count lags one interval. The two loops also wake the main actor 20x/s for the process lifetime in an idle menu-bar app. Fix: re-register inside `onChange` (continuation-driven loop) with a single coalesced pending update, or adopt `Observations` where the deployment target allows; test the icon-update cadence with an injected clock.

**Acceptance** (BA 2026-10-14) — Size **M**, one branch. Flag: the missed-update race is a reasoned scenario, not an observed one; the idle wake-up cost is measurable and is the QA check.
- Given an injected clock and a store whose `isRefreshing` goes true and then false 40 ms later with a new container count, when observation runs, then the icon renderer's last call reflects not-refreshing and the new count (no stuck refresh glyph).
- Given 100 store changes within one second, when observation runs, then icon updates are coalesced (at most one pending update at a time) and the final icon matches the final state.
- Failure path: given the app is idle (menu closed, refresh interval Manual), when observed for 10 seconds, then `StatusItemController` performs no timer-driven main-actor wake-ups (test with the injected clock: zero scheduled ticks).
- QA check (Mini): set refresh to Manual, close the menu, run `top -l 3 -s 5 -stats pid,command,idlew -pid <ContainerBar pid>`; IDLEW in samples 2 and 3 is under 5 per second (today about 20). Then press Refresh in the dashboard and screenshot the menu bar 2 seconds after the refresh finishes: the icon shows no refresh glyph.

### CB-075: Settings persistence: any decode failure silently wipes saved hosts/sections, and `MatchType` raw values are UI strings
**Priority**: Medium
**Description**: Audit 2026-09-18. `SettingsStore.loadHosts` treats a missing blob and an undecodable blob identically (`try?`, logged at `.info` as "No saved hosts found"), then `if hosts.isEmpty { addHost(.local) }` -> `saveHosts()` overwrites the user's remote-host configuration. `DockerHost` has non-optional fields, so any future non-optional addition or a bad write loses every SSH/TLS host on next launch; `SettingsStoreHostSectionTests` enshrines "Decode fails silently". `loadSections` has the same drop-everything behaviour, and `ContainerSection.MatchType` persists its UI label as the Codable raw value (`"Container name contains"`), so any copy edit breaks decoding of all saved sections; `.labelEquals` with an empty value can never match because `split` omits empty subsequences. Fix: distinguish nil from decode error, log at `.error`, copy the raw blob to a `.backup` key before seeding defaults, decode tolerantly (`decodeIfPresent` with defaults) behind a schema-version key, give `MatchType` machine raw values with a separate `displayName` and a one-time migration. Tests for each.

**Acceptance** (BA 2026-10-14) — Size **L**. Flag: **two branches** — (a) load safety for hosts and sections: distinguish missing from undecodable, log at `.error`, copy the raw blob to a `.backup` key before seeding, tolerant decoding behind a schema-version key (size M, first); (b) `MatchType` machine raw values with a `displayName`, a one-time migration, and the empty-value `labelEquals` case (size M, second; touches CB-085's editor validation).
- (a) Given saved hosts that include an SSH host and a stored blob that fails strict decoding (fixture: an entry missing a field added later), when the app launches, then the raw blob is copied to `dockerHosts.backup`, an `.error` log names the key, every host that tolerant decoding can recover is kept, and the saved hosts are not replaced by a local-only default while a backup is absent.
- (a) Given no saved hosts at all (first launch), when the app launches, then the local host is seeded and no backup key is written.
- (b) Given sections saved with the old raw value `"Container name contains"`, when the new build launches, then the sections decode, are rewritten once with the machine raw value, and the editor shows the same label text; a second launch performs no migration.
- (b) Failure path: given a `labelEquals` rule whose value is `env=` (empty value), when the editor saves it, then it is either rejected inline or stored so that it matches a container whose `env` label is empty (decision recorded in the PR); it never silently matches nothing.
- QA check (Mini, feature brief only, never the daily pass): back up with `defaults export com.tookes.ContainerBar /tmp/cbqa-defaults.plist`, quit ContainerBar, overwrite `dockerHosts` with a truncated copy of its data, relaunch. Pass: `defaults read com.tookes.ContainerBar dockerHosts.backup` prints the original data and Settings > Connections shows `QA Runtime` (or an error notice), never a silent local-only list. Restore with `defaults import`. The daily pass covers the plain relaunch case (lucius-daily-qa story 5 AC3).

### CB-077: Error surfacing: fetcher-init error replaced by "not configured", and a second action on a busy container is dropped silently
**Priority**: Medium
**Description**: Audit 2026-09-18. `ContainerStore.initializeFetcher` catches `DockerAPIClientImpl.init`'s `socketNotFound` (Docker Desktop not running — the common launch case) into `connectionError`, but `refresh()` then overwrites it with "Docker connection not configured", so the mapped "Docker not running. Please start Docker Desktop." (`ConnectionErrorMessage`) is never shown and the user is told to check configuration. `performContainerAction` never retries `initializeFetcher()`, so actions fail with "not configured" even after Docker starts, until the next refresh. Separately, `ContainerStore+Actions` `guard !actionInProgress.contains(id) else { return }` drops a second action (Stop then Start) with no `lastActionError` while `ContainerActionRouter` still logs it and reopens the menu; nothing tests the debounce. Fix: have `initializeFetcher()` return its error and route it through `userFriendlyConnectionErrorMessage` on both paths; set a "busy" state on the dropped path and skip `onMenuReopenRequested` when the id is in progress. Tests for both.

**Acceptance** (BA 2026-10-14) — Size **M**.
