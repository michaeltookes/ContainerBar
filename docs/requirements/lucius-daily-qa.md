## 1. Problem

ContainerBar's only automated checks today are CI (`swift-ci.yml` on GitHub-hosted runners) and four Prowl hunts (`prowl-qa.yml` on the Mini's self-hosted runner) that run a **Debug hunt-mode build** against `FixtureDockerAPIClient`: six fixed in-memory containers, a throwaway defaults suite, no real daemon, no SSH, no Sparkle. Nothing exercises the build users actually install (the notarized zip or the Homebrew cask) against a real container runtime, so a whole class of defect is invisible until a user hits it:

- Defects that only exist on the real transport: multiplexed log frames leaking into log text (CB-070), a peer-closed connection reported as "daemon may be incompatible" (CB-071), the aggregate memory denominator inflated by unlimited containers (CB-069), dual-stack port duplication (CB-079). Each was found by a code audit, not by a run.
- Defects that only exist in the distributed artifact: CB-041 (a resource-bundle path that worked from the build tree and crashed off it) is the precedent; the clean-machine smoke launch in `docs/RELEASING.md` is still a manual console step (CB-058).
- Settings that survive (or do not survive) a relaunch or an upgrade (CB-075).

How we know: the 2026-09-18 audit filed CB-069 to CB-098 from code reading alone; `docs/RELEASING.md` and CB-058 record that the launch half of the smoke test is manual; the owner asked on 2026-10-14 for Lucius to run automated QA on ContainerBar "throughout the day, similar to Sentwise". Sentwise already has this lane: a standing QA recipe file and briefs in Lucius' workspace, evidence under `artifacts/sentwise-qa/runs/`, a report per run, results posted to the product's Discord channel, a zero-token hourly check that posts failures only, and one summary a day.

## 2. Goal and non-goals

**Goal.** Every weekday, without the owner doing anything, Lucius proves on the Agent Mini that the **currently released** ContainerBar installs, launches, connects to a real container runtime, lists and acts on disposable QA containers, keeps its settings across a relaunch, and can check for updates; and the owner learns about a regression from one Discord message with evidence, the same day it appears.

**How we know it worked.** Measured weekly in the company metrics: a daily-pass clean rate (scheduled runs that ran and passed, out of scheduled runs), zero runs that touched anything outside the QA fixture, and the number of defects the pass found before a user did.

**Non-goals.**
- Not a replacement for CI or the Prowl hunts; those keep gating PRs on fixture data.
- Not branch or PR QA. Verifying a builder's branch is a separate, orchestrator-fired brief (factory Stage 3); the daily pass tests the released build only, plus the release-day upgrade case.
- No accessibility audit (CB-081 keeps the owner's manual VoiceOver pass as its check), no screenshots for marketing (CB-099), no performance benchmarking beyond the one idle-wakeup probe used by CB-073.
- No code or script changes in this repository as part of this brief. Any repo change the design needs (for example CB-058's automated console launch, or hiding hunt mode from release builds per CB-090) is its own backlog item and branch.
- No Docker Desktop on any Mac, ever (company rule).

## 4. Definitions used in the acceptance criteria

- **QA runtime**: rootless Podman owned by a dedicated unprivileged user `cbqa` on the homelab container host (`<qa-container-host>`), its API served by a system unit at `/run/cbqa-api/podman.sock`, and reached from the Mini over SSH as a second, forward-only account `cbqa-fwd` (architecture §2). Neither account has sudo, `docker` membership, or a systemd user manager. It runs **only** QA fixture containers; the host's own runtime and real services are invisible to it. No container runtime runs on any Mac (2026-10-12 decision).
- **QA control commands**: `ssh cbqa-ctl <verb>` from the Mini, a forced command on the host accepting only `status`, `info`, `reset`, `target-stop`, `api-stop`, `api-start` (contract in architecture §5). This is how a pass reads or changes the runtime outside the app; there is no `podman` CLI on the Mini.
- **QA fixture set**: containers created by `cbqa-ctl reset` (CB-100), every one named with the prefix `cbqa-` and carrying the label `com.tookes.containerbar.qa=1`, from small public images pinned by digest and pulled once (no pull during a pass). Six containers, five running:
  - `cbqa-web`: running, no memory limit, published `18080:80/tcp` and `18080:80/udp`.
  - `cbqa-logs`: running, no TTY, no memory limit, prints the exact lines `cbqa-line-1`, `cbqa-line-2`, `cbqa-line-3` to stdout and `cbqa-err-1` to stderr at start, then sleeps.
  - `cbqa-limited`: running, memory limit 256 MiB.
  - `cbqa-stopped`: created and exited (status Exited).
  - `cbqa-target`: running; the only container the pass may stop, start, or restart.
  - `cbqa-tty`: running with a TTY (`-t`), prints `cbqa-tty-line-1`, then sleeps; used only by CB-070's TTY check (replaces creating a temporary TTY container during a pass).
- **QA host entries**: two hosts in the Mini's ContainerBar settings, both pointing at the QA runtime. `QA Runtime`: SSH, runtime Podman, host `cbqa-tunnel` (an `~/.ssh/config` alias, so no address appears in the app or a screenshot), user `cbqa-fwd`, port 22, remote socket `/run/cbqa-api/podman.sock`; it is the selected host during every pass. `QA Runtime (socket)`: Unix Socket (Local), runtime Podman, socket stored as the expanded absolute path `/Users/<qa-mini-user>/qa/containerbar/podman.sock` (the app does not expand `~`; the setup run prints the path with `echo "$HOME/qa/containerbar/podman.sock"` and types that string into the Add Host sheet, and the recipe records it), which exists only while the pass's own SSH stream-local forward runs (the **Unix-socket leg**, Wednesday and Saturday, story 1 AC7).
- **Baseline settings**: refresh interval 10 seconds, Show stopped containers on, Launch at Login off, no sections, `QA Runtime` selected, Sparkle automatic checks off and first-launch prompt suppressed (`SUEnableAutomaticChecks = false`, `SUHasLaunchedBefore = true`). Exported once to `~/.openclaw/workspace/qa/containerbar/baseline.plist` on the Mini (private, never committed).
- **CI-idle check and desktop lock**: one mechanism shared with the Sentwise pass, defined in architecture §7 step 0 and used by story 6: the CI-busy predicate, busy if `pgrep -x Runner.Worker` returns a process or if `gh api repos/michaeltookes/sentwise/actions/runners` or `gh api repos/michaeltookes/ContainerBar/actions/runners` reports any of the runners registered on this host with `busy: true` (wait up to 10 minutes before a pass, no wait before each case), and the workspace desktop lock that the Sentwise daily pass takes, described in the brief's Environment preamble.
- **Released build**: the version in the latest non-draft GitHub release of `michaeltookes/ContainerBar` (today 2.0.4, build 7), signed by the owner's Developer ID, notarized and stapled.
- **Pass window**: the time box of one run (assumption: 20 minutes for the full pass, 1 minute for the hourly check).
- **Evidence root**: `~/.openclaw/workspace/artifacts/containerbar-qa/runs/<YYYY-MM-DD>-<kind>-<HHMM>/` on the Mini, where `<kind>` is `daily`, `hourly`, or `release`.
- **Test case ids**: `TC-CB-<n>` in `docs/qa/test-cases.md` (architecture §9E); each story below names its cases.

## 5. User stories and acceptance criteria

### US-lucius-daily-qa-1: A QA container runtime the Mini can reach that cannot reach production

As the owner, I want ContainerBar on the Mini to monitor a container runtime that holds only disposable QA containers, so that a daily pass can start, stop, and read logs from real containers without any path to a production service.

Backlog: **CB-100**. Design: solution architect (runtime topology). Execution: homelab IT specialist.

- **AC1 (runtime reachable).** Given the QA runtime is provisioned, when Lucius runs `ssh cbqa-ctl status` from the Mini, then it exits 0 and lists exactly the six fixture containers in section 4 with the stated states, and nothing else.
- **AC2 (fixture only).** Given `cbqa-ctl status` lists **all** of `cbqa`'s containers (it applies no filter), when Lucius reads it, then every container name starts with `cbqa-`. Any other name is a FAIL of the precondition and the pass stops before launching ContainerBar.
- **AC3 (no production path).** Given only the lane's two keys on the Mini, when an operator tries each of: (a) forwarding the host's system runtime socket through `cbqa-tunnel` and calling `/_ping` on it, (b) `ssh cbqa-ctl 'podman ps'` or any verb outside the list, (c) `ssh cbqa-tunnel touch /tmp/cbqa-p2-probe` (a session on the tunnel key), (d) a TCP forward through the tunnel key, exercised with a client connection (probe P3), (e) forwarding a systemd user bus or manager socket (probe P5), then (a) fails with permission denied (neither account is in the `docker` group or has sudo), (b) exits 64, (c) exits non-zero with `nologin`'s account-unavailable message and `/tmp/cbqa-p2-probe` does not exist on the host (the tunnel key's forced command `/usr/bin/false` replaces the requested one), (d) the local connection gets no banner and ssh logs `administratively prohibited` (`AllowTcpForwarding no`), and (e) fails because no user manager exists for either account; while the app's own forward of `cbqa`'s Podman socket still works (story 4 AC1). Enforcement: Linux user and group isolation, no systemd user manager for either account (no linger, `pam_systemd` skipped), `authorized_keys` options (tunnel key on `cbqa-fwd`: `restrict,port-forwarding,command="/usr/bin/false"`; control key on `cbqa`: `restrict,command="<cbqa-home>/bin/cbqa-ctl"`), and `Match User` blocks in `sshd_config` (architecture §2, §6).
- **AC4 (reset).** Given any fixture container is missing or in the wrong state (for example `cbqa-target` left stopped by an aborted run), when `ssh cbqa-ctl reset` runs, then AC1 holds again within 2 minutes (design target: 20 seconds), and the reset touches only containers carrying the QA label. The same reset runs from the system timer `cbqa-reset.timer` (as `cbqa`) at 06:45 Central every day.
- **AC5 (runtime down, unhappy path).** Given the QA runtime is unreachable (host down, SSH refused, or `cbqa-ctl status` exits 2), when the pass precondition check runs, then it retries once after 60 seconds, and if still unreachable the pass is marked BLOCKED with reason `qa-runtime-down`, the Discord message says so in one line, and no ContainerBar case is attempted (no product case is marked FAIL).
- **AC6 (no container runtime on the Mini).** Given the Mini, when `ls /Applications | grep -i -e docker -e podman` and `command -v docker podman` run, then both print nothing; the lane never installs Docker Desktop or a Podman machine on a Mac.
- **AC7 (Unix-socket leg).** Given a Wednesday or Saturday pass, when Lucius prepares the socket path (stops a forward this lane left behind, identified by `$HOME/qa/containerbar/forward.pid` and its command line, by that PID only; `rm -f` a stale socket file), starts `ssh -nNT -o ExitOnForwardFailure=yes -o StreamLocalBindUnlink=yes -L "$HOME/qa/containerbar/podman.sock":/run/cbqa-api/podman.sock cbqa-tunnel` in the background, writes its PID to `forward.pid`, and sees the socket file appear within 10 seconds (else the leg's cases are `blocked` with reason `forward-failed`), then selects `QA Runtime (socket)`, then story 4 AC1 holds through ContainerBar's local Unix-socket transport (TC-CB-11). With the forward not running, selecting the same host shows an error that names the socket or runtime, not "not configured" (TC-CB-12, known failure until the installed release contains CB-077, story 7 AC4). At the end of the leg Lucius stops the forward by its recorded PID only, removes the socket file, and selects `QA Runtime` again.

**Technical tasks (CB-100).**
- homelab-it, on `<qa-container-host>` (homelab repo, never this one), exactly as architecture §2: accounts `cbqa` (owns the containers) and `cbqa-fwd` (forward-only, shell `/usr/sbin/nologin`, member of group `cbqa` only; `cbqa` keeps `/bin/sh` so its forced `cbqa-ctl` can run), neither with sudo or `docker`; `loginctl disable-linger` for both; `pam_systemd` skipped for both in `/etc/pam.d/sshd` (`session [success=1 default=ignore] pam_succeed_if.so quiet user in cbqa:cbqa-fwd` before the `pam_systemd` line), so neither ever gets a systemd user manager or user bus.
- homelab-it: the system unit `cbqa-podman.service` (`User=cbqa`, `Group=cbqa`, `RuntimeDirectory=cbqa`, `RuntimeDirectoryPreserve=yes`, `XDG_RUNTIME_DIR=/run/cbqa`, `UMask=0007`, `KillMode=process`, `Delegate=yes`, `podman system service --time=0 unix:///run/cbqa-api/podman.sock`), `tmpfiles.d` entry `/run/cbqa-api 0750 cbqa cbqa`, `cbqa`'s `containers.conf` (`cgroup_manager = "cgroupfs"`, `events_logger = "file"`), the system timers `cbqa-reset.timer` (06:45 Central) and `cbqa-podman-revive.timer` (`OnActiveSec=5min`, `RemainAfterElapse=no`; `api-stop` re-arms it with `systemctl restart`), and a polkit rule that lets only `cbqa` start/stop/restart `cbqa-podman.service` and start or restart `cbqa-podman-revive.timer`. If the memory limit on `cbqa-limited` cannot be applied without a user manager, drop the limit from that fixture and record it; do not re-enable a user manager.
- homelab-it: `cbqa-ctl` at `<cbqa-home>/bin/cbqa-ctl` with the verbs `status`, `info`, `reset`, `target-stop`, `api-stop`, `api-start` (contract in architecture §5; container verbs via `podman --remote --url unix:///run/cbqa-api/podman.sock`); any other verb exits 64; fixture images pinned by digest; `reset` touches only containers carrying the QA label.
- Orchestrator, on the Mini: generate `~/.ssh/cbqa_tunnel_ed25519` and `~/.ssh/cbqa_ctl_ed25519` (ed25519, no passphrase, mode 600). homelab-it authorises the tunnel key in `cbqa-fwd`'s `authorized_keys` as `restrict,port-forwarding,command="/usr/bin/false"` and the control key in `cbqa`'s as `restrict,command="<cbqa-home>/bin/cbqa-ctl"`, and adds the `sshd_config` blocks `Match User cbqa-fwd` (`AllowTcpForwarding no`, `AllowStreamLocalForwarding local`, `AllowAgentForwarding no`, `X11Forwarding no`, `PermitTunnel no`, `PermitTTY no`) and `Match User cbqa` (the same, but `AllowStreamLocalForwarding no`); validate and reload sshd.
- Orchestrator: `~/.ssh/config` aliases `cbqa-tunnel` (`User cbqa-fwd`, `IdentityFile ~/.ssh/cbqa_tunnel_ed25519`, `IdentitiesOnly yes`, `StreamLocalBindUnlink yes`) and `cbqa-ctl` (`User cbqa`, `IdentityFile ~/.ssh/cbqa_ctl_ed25519`, `IdentitiesOnly yes`); the host key in `~/.ssh/known_hosts` from the fingerprint homelab-it reads on the host (not a blind `ssh-keyscan`), because ContainerBar runs `ssh` with `StrictHostKeyChecking=yes` and `BatchMode=yes`; `mkdir -p -m 700 "$HOME/qa/containerbar"`.
- homelab-it, after provisioning, runs probes P1–P6 from the Mini and records the results; all must hold before CB-100 is done: (P1) the app's exact argv (`ssh -nNT … -L <local.sock>:/run/cbqa-api/podman.sock cbqa-tunnel`) creates the local socket and `curl --unix-socket <local.sock> http://d/_ping` prints `OK`; (P2) `ssh cbqa-tunnel touch /tmp/cbqa-p2-probe` exits non-zero (OpenSSH runs the forced `/usr/bin/false` through the account's shell, `nologin`, which prints its account-unavailable message; that message is accepted) and, on the host, `/tmp/cbqa-p2-probe` does not exist, proving no requested command ran; `ssh cbqa-ctl id` exits 64; (P3) the TCP forward is exercised, not just requested: start `ssh -N -o ExitOnForwardFailure=yes -L 15432:localhost:22 cbqa-tunnel` in the background and record its PID, wait 2 seconds, run `nc -w 5 127.0.0.1 15432 </dev/null`, and assert it prints nothing (an allowed forward would print the host's `SSH-2.0-` banner) and that the ssh process's stderr contains `administratively prohibited`; then stop that recorded PID; (P4) forwarding the host's system runtime socket through `cbqa-tunnel` gives permission denied on use; (P5) no user bus is reachable: with a tunnel open, forwarding `/run/user/<cbqa-uid>/bus`, `/run/user/<cbqa-uid>/systemd/private` and `/run/user/<cbqa-fwd-uid>/bus` each fails on use (no such file), and on the host `/var/lib/systemd/linger/cbqa` and `/var/lib/systemd/linger/cbqa-fwd` do not exist, `systemctl is-active user@<cbqa-uid>.service user@<cbqa-fwd-uid>.service` reports `inactive` for both, and `loginctl list-users` shows neither account while a tunnel is up (with no linger and `pam_systemd` skipped there is no logind user object, so `loginctl show-user` would only error); (P6) two consecutive outage cycles recover: `ssh cbqa-ctl api-stop`, wait up to 6 minutes for the revive timer, `ssh cbqa-ctl status` exits 0 with all fixtures still running and `startedAt` unchanged; repeat once more (the second cycle proves the timer re-arms); then `api-stop` followed at once by `api-start` recovers the same way (proves `/run/cbqa` survived the stop).
- QA case: TC-CB-05 (remote Podman socket at a custom path, user `cbqa-fwd`) doubles as the one-time setup run that adds both host entries through Settings.

### US-lucius-daily-qa-2: A standing recipe file and evidence layout in Lucius' workspace

As Lucius, I want one recipe file that tells me how to find and drive ContainerBar's status item, dashboard, Settings panes, and dialogs on the Mini, so that each pass follows known steps instead of rediscovering the UI and two runs of the same case produce comparable evidence.

Backlog: **CB-101**. Mirrors `SENTWISE_QA.md`.

- **AC1 (file exists).** Given the workspace, when the orchestrator opens `~/.openclaw/workspace/CONTAINERBAR_QA.md`, then it contains: the released-build verification commands; the status-item click recipe; how to tell the released app's status item from the Prowl hunt build's (bundle id `com.tookes.ContainerBar.hunt`) if both are present; the Settings pane names (General, Connections, Sections, About) and the accessibility identifiers the pass may use (`refreshIntervalPicker`, `testConnection`, `refreshLogs`, `logs-panel-close`, `aboutVersion`, `dismissActionError`, `quitApp`, `openSettings`, `containerCard-<slug>`, and, once the installed release contains CB-107 (the release-aware `fixed-in` rule, story 7 AC4), `containerBarStatusItem`, `containerStop-<slug>-<short-id>`, `containerStart-<slug>-<short-id>`, `logs-panel-container-<slug>-<short-id>`, `logsPanelText`, `connectionStatus`, `checkForUpdates-about`, `showStoppedToggle`; until then the recipe falls back to labels such as `Stop container cbqa-target`, after hovering the card, because the quick actions are only in the tree on hover today); the forbidden controls list (AC4); the fixture set; the evidence root; and the restore steps.
- **AC2 (layout).** Given a finished run, when the orchestrator lists its evidence root, then it contains `report.md`, `assets/<TC-id>/NN-<slug>.png` for every executed step, and one `assets/<TC-id>.mp4` (Peekaboo records MP4) for each video case and no others: TC-CB-08, TC-CB-10, TC-CB-13, TC-CB-15, TC-CB-16, TC-CB-17 (the cases that mutate state; same list as architecture §9E), using the report shape of the existing Lucius brief template.
- **AC3 (no secrets in assets).** Given any asset in the evidence root, when it is reviewed, then it shows no SSH private key, password, token, real host address, or non-fixture container name. A screen capture that would show one is cropped (`screencapture -R`) or not taken, and the step is marked `blocked` instead.
- **AC4 (forbidden controls).** Given the recipe, when it lists forbidden actions, then it includes: Remove container on any container; any action on a container whose name does not start with `cbqa-`; Remove Host or Delete Section on any entry other than one the run itself created; "Install Update" in a Sparkle dialog during a daily pass; the Launch at Login toggle; the global keyboard shortcut recorder.
- **AC5 (stale recipe, unhappy path).** Given a recipe step whose element is not found (the UI changed in a release), when Lucius follows it, then the step is marked `blocked` with the actual `peekaboo see` element list attached as text in the report, the case does not improvise a different click path, and the report's "Defects and proposed backlog items" names the recipe as stale.

**Technical tasks (CB-101).**
- Orchestrator: write `~/.openclaw/workspace/CONTAINERBAR_QA.md` (the recipe) and the brief `~/.openclaw/workspace/tasks/<date>-containerbar-daily.md` with the standard Environment preamble; commit both in the workspace repo.
- Orchestrator: after the TC-CB-05 setup run, set the Sparkle preferences in the baseline (section 4) and export `baseline.plist`. The plist is used only as the fallback restore (story 6 AC4); normal restores go through the UI.
- Docs (project-planner or a docs builder, this repo): `docs/qa/test-cases.md` with TC-CB-01..17 in the project-planner format, and `docs/qa/seed-data.md` with the fixture table, the baseline, and the host entries, all with placeholders (architecture §9E, §4).
- Builder, new backlog item for the BA to file ("QA-hooks accessibility identifiers"): the identifiers in architecture §9A1–A6, including keeping the quick-action buttons in the accessibility tree when visually hidden, and the matching `.prowl/config.yml` forbidden selectors. The pass can start before it merges; it makes the recipe stop depending on hover and labels.

### US-lucius-daily-qa-3: Install path and released-build integrity

As the owner, I want each daily pass to confirm the Mini runs exactly the released build, and on release day to install the new build from both the cask and the notarized zip, so that a broken artifact, a wrong signature, or a stale cask is caught before users install it.

Backlog: **CB-102**. Related: CB-058 (automating the console launch of the zip), CB-086 (validator from a clean checkout).

- **AC1 (daily, version matches).** Given the latest GitHub release is version V, when the pass reads `defaults read /Applications/ContainerBar.app/Contents/Info.plist CFBundleShortVersionString`, then it prints V. If it prints anything else, the pass is marked FAIL with reason `stale-install` and continues the remaining cases against the installed build, saying so in the report.
- **AC2 (daily, signature).** Given the installed app, when the pass runs `codesign --verify --deep --strict /Applications/ContainerBar.app`, `spctl --assess --type execute /Applications/ContainerBar.app`, and `xcrun stapler validate /Applications/ContainerBar.app`, then all three exit 0, and `codesign -dv` names the owner's Developer ID authority (the expected authority string lives in the recipe file, not here).
- **AC3 (daily, launch).** Given ContainerBar is not running, when Lucius launches it from the console session with `open /Applications/ContainerBar.app`, then within 10 seconds a ContainerBar status item is visible in the menu bar (screenshot `01-status-item.png`) and `pgrep -x ContainerBar` prints one PID. If no status item appears within 10 seconds, the case is FAIL with the last 50 lines of `log show --last 2m --predicate 'process == "ContainerBar"'` attached as text, plus the newest `~/Library/Logs/DiagnosticReports/ContainerBar-*.ips` file name if one appeared. (Feasibility note: the app does not bootstrap swift-log to OSLog, so this shows system messages about the process, not the app's own log lines; the optional OSLog item in architecture §9D fixes that.)
- **AC4 (release day, cask).** Given a new release V+1 has been published and the tap updated, when the orchestrator fires the release brief and Lucius runs `brew upgrade --cask containerbar`, then the installed version reads V+1, AC2 and AC3 pass, and the saved QA host entry and refresh interval from before the upgrade are unchanged (see story 5).
- **AC5 (release day, zip).** Given the same release and the installed ContainerBar quit first through its Quit button (two copies with one bundle id must not run at once), when Lucius downloads `ContainerBar.zip` from the release into a new temporary directory, extracts it, and runs the same three checks as AC2 against the extracted app, then all pass, the extracted app launches from the console session (status item visible), is quit, the temporary directory is deleted, and the installed app is relaunched. This closes the manual step recorded in `docs/RELEASING.md` for that release.
- **AC6 (release day, Sparkle upgrade path, TC-CB-13).** Given the installed app is quit and a copy of the previous release V is extracted from its zip into a new temporary directory, when Lucius launches it and chooses "Check for Updates..." in Settings > About, then Sparkle offers V+1 with the release notes from the appcast. Lucius presses **Remind Me Later** (never Install Update, never Skip This Version, which persists), quits that copy, deletes the temporary directory, and relaunches the installed app.
- **AC7 (unhappy path, Gatekeeper).** Given an artifact fails any of `codesign`, `spctl`, or `stapler`, when the check runs, then the run is FAIL with the exact tool output quoted in the report, the Discord message starts with `QA FAIL` and names the failing check, and Lucius does not launch that artifact.

QA cases: TC-CB-01, TC-CB-02 (daily); TC-CB-13 and the cask and zip checks (release brief only). Technical task: none in the app beyond CB-074 for a deterministic update button; release-prep must keep old releases' `ContainerBar.zip` downloadable.

### US-lucius-daily-qa-4: Dashboard, container list, actions, and logs against the QA runtime

As the owner, I want the daily pass to open the dashboard, see the fixture containers with correct state and metrics, stop and start one container, and read its logs, so that the core of the product is verified on a real runtime every day.

Backlog: **CB-103**.

- **AC1 (connected list).** Given the QA host entry is selected and the fixture set is in its reset state, when Lucius clicks the status item, then the dashboard opens and shows all six `cbqa-` containers within one refresh interval; `cbqa-web`, `cbqa-logs`, `cbqa-limited`, `cbqa-target`, and `cbqa-tty` are shown as running and `cbqa-stopped` as stopped (or hidden, if "Show stopped containers" is off, which the recipe states).
- **AC2 (counts and metrics).** Given the dashboard is open, when Lucius reads the Running pill and the General Stats grid, then the Running count equals 5, the CPU and RAM tiles show numbers with units, and the RAM tile's denominator is not larger than the QA runtime's total memory (`memTotal` from `ssh cbqa-ctl info`, ±0.1 GB). The last check fails on today's build because of CB-069; the pass records it as a known failure linked to CB-069 rather than a new defect.

## 6. Constraints

- **Platform.** Apple Silicon only, macOS 14+ (`depends_on arch: :arm64`). The Mini runs the released build only; it keeps `~/qa/ContainerBar` for CI, which the pass never builds or launches.
- **Shared desktop.** The Mini's self-hosted runners run `prowl-qa` for this repo (hunt build, bundle id `com.tookes.ContainerBar.hunt`, its own status item) and for Sentwise. Story 6 AC2 applies to every full pass and every release brief. CB-090 item 1 (a concurrency group for `prowl-qa.yml`) and ops backlog 6l (separate runner user) reduce the collision rate but do not remove the precondition.
- **Hunt mode in release builds.** Release builds still contain the hunt-mode switch (CB-090 item 4). The pass must never set `CONTAINERBAR_HUNT_MODE`; the released app must show the QA runtime's containers, not the six fixtures. Seeing the fixture names (`FixtureDockerAPIClient`) in a daily pass is a FAIL.
- **Sparkle.** A daily pass checks for updates but never installs; installs happen only in the release brief. CB-074 (updater started in hunt mode) is a related defect on the CI side.
- **Container runtime.** No Docker Desktop and no Podman machine on any Mac (2026-10-12 decision). ContainerBar supports a local Unix socket and a remote host over an SSH tunnel or TCP+TLS. Access to a Docker or Podman API socket is equivalent to full control of that daemon, so the QA runtime is a rootless Podman owned by `cbqa` that runs nothing but QA fixtures (story 1 AC3). The local Unix-socket transport is exercised through an SSH-forwarded socket (story 1 AC7).
- **Mini resources.** The Mini also hosts the CI runners, the OpenClaw gateway, and a local embedding server. The chosen design adds no VM: only ContainerBar itself and one `ssh` process (two during the Unix-socket leg).
- **Cost.** Lucius runs on the owner's ChatGPT subscription. The hourly check is zero-token; full passes are model-driven and time-boxed (20 minutes assumed).
- **Process control.** On the Mini an agent may stop only a process it started, by PID. ContainerBar is quit through its own menu or an `osascript quit`, never by signal. Nothing in this lane runs on the owner's MacBook or development Mini.
- **Public repository.** This file and the backlog are public mirrors. Host addresses, user names, channel ids, key paths, and the Developer ID authority string live in the workspace recipe file on the Mini.

## 7. Data and privacy notes

- **What leaves the Mini.** The report path and summary text, and selected screenshots and videos, go to a private Discord channel. Assets show only fixture containers and the QA runtime's name. No asset is committed to this public repository.
- **What is stored.** Evidence under `~/.openclaw/workspace/artifacts/containerbar-qa/runs/` on the Mini; retention follows the Sentwise runs (assumption: 30 days, then pruned by the workspace's existing housekeeping).
- **Credentials.** Two keys dedicated to this lane (story 1 technical tasks): a tunnel key for the forward-only account `cbqa-fwd`, and a control key for `cbqa` that can only run `cbqa-ctl`. Neither has a passphrase (so no prompt blocks an unattended run), each is authorised only for its one account on the QA host, and neither is ever printed, screenshotted, or posted. ContainerBar runs `/usr/bin/ssh`, which picks the tunnel key up from the `cbqa-tunnel` alias in `~/.ssh/config` (or the SSH agent if one is loaded); the app stores no key material itself.
- **ContainerBar's own data.** The app keeps hosts, sections, and settings in its user defaults on the Mini. The pass reads and changes them only through the UI (story 5), restores the baseline, and never edits the preferences file directly in a daily pass.
- **No consent copy changes.** The app sends nothing to Genkei services; this lane adds no telemetry.
