# ContainerBar - Resolved Items

## ~~CB-066: Unix-socket/SSH request path retries non-idempotent requests; TLS path guards on `isIdempotent`, Unix path does not~~
**Resolved**: 2026-09-21 (PR #57, branch transport-liveness, commits `78281d5` and `8593f1a`)
**Description**: `DockerAPIClientImpl+UnixSocket.performRequest` caught any non-cancellation error, optionally closed/reconnected, and then unconditionally issued the request a second time, so a `POST /containers/x/restart` whose socket or SSH tunnel dropped after the daemon had received it was replayed and the container restarted twice (or `stop?t=` was re-issued). It also retried after parse errors. The TLS path already had `guard request.isIdempotent`. **Fix — a shared, explicit retry policy on `HTTPRequest`:** `HTTPRequest` (`Sources/ContainerBarCore/API/HTTPTypes.swift`) gained `allowsRetryAfterSend: Bool`, defaulting from the method (`GET`/`HEAD`/`PUT`/`DELETE`/`OPTIONS`/`TRACE` true, `POST` and anything else false) and overridable per request; `removeContainer` (`DockerAPIClientImpl.swift`) passes `allowsRetryAfterSend: false` because a `DELETE /containers/{id}?force=true` is destructive even though the verb is nominally idempotent. `NWConnectionTransport.sendRequest` now throws a dedicated `HTTPRequestNotSentError` when there is no live `NWConnection` to send on, so callers can distinguish "never left the client" from "sent, response unknown". **Unix/SSH path:** `performRequest` was split so the connection-acquisition failure and the send failure call `retryUnixSocketRequest(_:after:sendWasAttempted:failedConnection:)` with `sendWasAttempted` false/true respectively; the retry is gated by the pure `static shouldRetryUnixSocketRequest(_:after:sendWasAttempted:)`, which returns false for `CancellationError`, true for `HTTPRequestNotSentError`, and otherwise `!sendWasAttempted || request.allowsRetryAfterSend`. Connection close on failure was narrowed to the captured failed connection (`shouldCloseCapturedUnixSocketConnection`), and the SSH-tunnel reconnect decision was extracted into `shouldReconnectSSHTunnelForUnixSocketRetry(connectionType:tunnelState:)` so a dead tunnel is relaunched even when the failure happened before a `UnixSocketConnection` was acquired (commit `f716924`). **TLS path:** `DockerAPIClientImpl+TLS.performRequest` keeps `shouldRetryTLSRequest(after:)` (only `.connectionFailed`/`.networkTimeout`/`.tlsConnectionFailed` are retryable) and now guards on `request.allowsRetryAfterSend` instead of `isIdempotent`; an `HTTPRequestNotSentError` re-runs `ensureTLSConnected()` and resends without the retryable-error check because nothing reached the wire. `HTTPRequest.isIdempotent` still exists but no longer has callers in `Sources/`. **Tests (`Tests/ContainerBarCoreTests/TransportRequestTimeoutTests.swift`, Swift Testing):** `unixSocketRetryPolicyDoesNotReplayNonIdempotentSends` pins the policy table — a `POST …/restart` retries when the send was never attempted and does not retry after a send; the same request retries after `HTTPRequestNotSentError`; the opted-out `DELETE …?force=true` does not retry after a send; a `GET …/containers/json` does. `unixSocketCleanupRequiresCapturedFailedConnection` and `sshTunnelReconnectDoesNotRequireCapturedUnixConnection` cover the two extracted predicates. **Not covered here:** an end-to-end `performRequest` test against a transport that drops mid-response on each path remains listed under CB-092, and the SSH tunnel stderr drain / single-flight `reconnect()` remain CB-067.

## ~~CB-062: Transport liveness: connect and request deadlines, handle `.waiting`, cancellable receives~~
**Resolved**: 2026-09-20 (branch transport-liveness)
**Description**: Nothing in the `NWConnection`-backed transport stack had a deadline, and a non-terminal connection state was dropped, so a bad endpoint (wrong TLS port, sleeping host, firewall drop, hung daemon) could wedge the app's refresh loop forever — the "refreshing" spinner never clearing and a host switch unable to tear the client down. **Three defects fixed. Defect 1 — `.waiting` dropped:** `NWConnectionTransport.awaitConnectionReady` (`Sources/ContainerBarCore/API/NWConnectionTransport.swift`) handled `.ready`/`.failed`/`.cancelled` and `default: break`, so an `NWConnection` parked in `.waiting(ECONNREFUSED/EHOSTUNREACH)` never resumed the continuation and `connectLocked` → `startConnection` → `awaitConnectionReady` suspended forever holding `ioGate`. Now a new `case .waiting(let error)` clears the state handler, cancels the connection, and resumes throwing `config.mapStateFailure(error)`. Fail-fast is the correct policy here: this is a polling menu-bar app that reconnects on the next refresh, and `.waiting` for a local socket or a LAN Docker host means the connection cannot currently be established (refused/unreachable/wrong port), so surfacing the mapped failure and letting the next poll retry beats suspending indefinitely; `.ready`/`.failed`/`.cancelled` are unchanged. **Defect 2 — no connect timeout:** neither `TLSConnection.swift` nor `UnixSocketConnection.swift` set a TCP `connectionTimeout`, so the OS never forced a bounded transition. Both `makeConnection` closures now build `NWProtocolTCP.Options` with `connectionTimeout` (`Int(15)` s) and pass them into `NWParameters` (`NWParameters(tls:tcp:)` for TLS; the Unix path builds `NWParameters(tls: nil, tcp:)` explicitly instead of `.tcp`). This is OS-level defense-in-depth behind the app-level deadline. **Defect 3 — no request deadline, non-cancellable receive:** `sendRequest` ran send + `receiveHTTPResponse` inside `ioGate` with no deadline, and `receiveChunk` (`HTTPReceive.swift`) used a `withCheckedThrowingContinuation` that ignored Task cancellation, so a daemon that accepts the connection and then never replies hung the receive forever — and because everything sits behind `ioGate`, a hung connect/receive also blocked `disconnect()` (TLS waits on the gate) and `TLSConnectCoordinator.reconnect`. **App-level deadline mechanism:** because `NWConnection`'s completion callbacks are not Task-cancellable, a new `withDeadline(seconds:connection:operation:)` helper (split into its own file `Sources/ContainerBarCore/API/TransportDeadline.swift` to keep the 247-line transport under the ~300-line guideline) races `operation()` against `Task.sleep`; if the sleep wins it calls `connection.cancel()` (which resumes the pending continuation with an error) and throws `DockerAPIError.networkTimeout`; if the operation wins the sleep is cancelled and the operation's own result/error propagates unchanged (so a fast, real connect failure still surfaces its specific `DockerAPIError`, not a timeout). Structured concurrency guarantees the cancelled child is awaited before returning and `connection.cancel()` guarantees it completes, so no suspended task leaks. `startConnection` wraps `awaitConnectionReady` with `config.connectTimeout`; `sendRequest` wraps send + `receiveHTTPResponse` with `config.requestTimeout`. `receiveHTTPResponse` and `receiveChunk` additionally call `Task.checkCancellation()` at the top so a cancelled parent Task stops instead of spinning (the deadline cancelling the connection remains the primary unblock); `IncrementalHTTPResponseParser` was not changed. **Timeouts are configurable/injectable:** `NWConnectionTransport.Config` gained `connectTimeout` (default 15 s) and `requestTimeout` (default 30 s) rather than a literal buried in the send/receive path — 15 s is generous for a slow TLS handshake over a LAN/VPN yet fails a wrong port or sleeping host well before the refresh loop notices, and 30 s sits comfortably above a normal Docker list/inspect round-trip while still bounding a silent daemon; each production transport owns matching constants and passes them in, and tests inject sub-second values. `DockerAPIError.networkTimeout` already existed and was marked transient in `DockerAPIError+Retry.swift` but nothing in Core ever produced it — the deadline paths now do. **Every existing transport behavior is preserved:** `ioGate` serialization, the `disconnectWaitsForGate` policy (TLS waits, Unix bypasses), `connectLocked`'s connect coalescing and `.wait`/`.ready` branches, `adoptConnection`, `cleanUpFailedConnection` (TLS `nil` policy and the Unix `shouldCleanupFailedConnection` predicate), the state-handler `self`-retention avoidance (only the mappers captured), and the non-timeout error taxonomy. **Tests (`Tests/ContainerBarCoreTests/NWConnectionTransportLivenessTests.swift`, Swift Testing, hermetic via an in-process `NWListener` on `127.0.0.1`/OS-assigned port pointed at by a plain-TCP `NWConnectionTransport` with injected tiny timeouts; every awaited call wrapped in a `withTestTimeout` race so a regression that reintroduces the hang fails the test instead of hanging `swift test`):** `requestDeadlineFiresOnSilentServer` — a listener that accepts but never sends a byte; `sendRequest` throws `DockerAPIError.networkTimeout` at ~the injected 0.2 s deadline (the core CB-062 regression guard, deterministic across repeated runs at ~0.218 s); `connectToRefusedPortFailsFast` — a port whose listener is fully torn down (awaiting `.cancelled`, which removed an accept race an early draft hit) refuses the connect, and connect throws a `DockerAPIError` promptly (proves the `.waiting` handling + connect bound); `happyPathReturnsParsedResponse` — a listener returning a minimal HTTP/1.1 200 response; `sendRequest` returns the parsed `HTTPResponse` without a timeout (proves the deadline does not fire on a fast healthy response and the plumbing is intact). **Test counts:** 285 before (276 pass + 9 skipped) → 288 after (279 pass + 9 skipped, 0 failed); +3 new passing tests, suite wall-clock ~7 s. **Validation on the Lucius Mac mini (Xcode 26.6 / Swift 6.3.3; CI Swift 6.2 on macos-15 is authoritative):** `swift build` clean, `swift test` 288 (279 pass + 9 skip, 0 fail), `swiftlint lint --quiet` (0.65.1) exits 0 with no new warnings in the changed source or test files. **Follow-up:** CB-064 (refresh cancellation / generation fencing) is the intended next step and will cancel `ContainerStore`'s in-flight refresh against these deadlines so a host switch tears the client down cleanly. **Review addition:** on a request deadline `sendRequest` now also runs the transport's connect-failure cleanup (`cleanUpFailedConnection`) so the transport stops reporting `isConnectedState() == true` for a connection the deadline just cancelled; without it the next request went out on the dead connection and failed once before the TLS coordinator / Unix close path reconnected. The silent-server test asserts `isConnectedState()` is false after the timeout.

## ~~CB-063: Chunked parser overflow and body-cap bypass~~
**Resolved**: 2026-09-18 (branch chunked-parser-limits)
**Description**: Fixed two defects in the chunked-transfer decode path of `IncrementalHTTPResponseParser` (`Sources/ContainerBarCore/API/IncrementalHTTPResponseParser.swift`), both remote-triggerable by any Docker/Podman daemon the app talks to over TLS/SSH. **Defect 1 — integer-overflow trap (crash):** `scanChunkSize` accepted any hex token up to `UInt64(Int.max)` and returned `Int(chunkSize)`; the `scanChunkedBodyEnd` loop then computed `let need = chunkSize + Self.lineSeparator.count`, so a chunk-size line of `7fffffffffffffff` (Int.max) made `Int.max + 2` overflow and **trap**, killing the process. **Defect 2 — body-cap bypass:** the `decodedTotal <= maxBodySize` check ran only *after* the full chunk payload was buffered and located, so a single declared chunk of e.g. `10000000` (256 MB) accumulated in the buffer far past the 128 MB `maxBodySize` before rejection. **Fix (a pre-buffer budget guard):** immediately after obtaining `chunkSize` and after the `chunkSize == 0` trailer branch — *before* computing `need`/`payloadEnd` — the loop now computes `let remaining = maxBodySize - decodedTotal` (non-negative by the loop invariant that `decodedTotal <= maxBodySize`) and throws the body-limit error (`DockerAPIError.tlsConnectionFailed("HTTP response body exceeded \(maxBodySize) bytes")`, reused verbatim so behavior/tests stay consistent — error-taxonomy work is the separate CB-071 and was not touched here) when `chunkSize > remaining`. This rejects the declared oversized chunk before any payload is buffered (fixing defect 2) and bounds `chunkSize` by `maxBodySize` (128 MB) so the subsequent `need` addition can never approach `Int.max` (fixing defect 1). The post-add `decodedTotal += chunkSize` / `decodedTotal <= maxBodySize` check is left in place as harmless defense-in-depth. **`scanChunkSize` decision:** left unchanged (still parses and returns the value, keeping its existing `chunkSize <= UInt64(Int.max)` guard that rejects tokens above Int.max as `invalidResponse`); the budget check stays in the loop where `decodedTotal` is in scope, because a chunk under the cap but exceeding the *remaining* cumulative budget must also be caught — a `scanChunkSize`-local `> maxBodySize` check could not see cumulative usage. The non-chunked/content-length path, header parsing, `enforceChunkMetadataLimit`, trailer scanning, and cursor-persistence logic were untouched. **Tests (`Tests/ContainerBarCoreTests/IncrementalHTTPResponseParserLimitTests.swift`, Swift Testing, injected small `maxBodySize`):** `chunkSizeAtIntMaxRejectedNoTrap` pins defect 1 — a `7fffffffffffffff` size line is now rejected as a thrown body-limit `DockerAPIError` instead of trapping; `chunkSizeAboveIntMaxRejected` pins the boundary above Int.max (`ffffffffffffffff`) still mapping to `invalidResponse` via the existing `scanChunkSize` guard; `oversizedChunkRejectedBeforeBuffering` pins defect 2 — with `maxBodySize` 1024 a chunk declaring `2000` (8192) plus only three payload bytes is rejected on the size line, proving the cap fires on the declared size, not the buffered bytes; `cumulativeChunksOverCapRejected` pins the cumulative case (three 5-byte chunks against `maxBodySize` 12, rejected at the third that crosses the line, guarding the `remaining` subtraction and the loop invariant); `multiChunkUnderCapStillDecodes` is the happy-path regression (a two-chunk body assembles to `hello world`). Because a committed overflow test would abort the whole `swift test` run with SIGILL/SIGTRAP, the fix was written and committed before the tests. **Test counts:** 280 before (271 pass + 9 skipped) -> 285 after (276 pass + 9 skipped, 0 failed); +5 new passing tests. **Validation on the Lucius Mac mini (Xcode 26.6 / Swift 6.3.3; CI Swift 6.2 on macos-15 is authoritative):** `swift build` clean, `swift test` 285 (276 pass + 9 skip, 0 fail), `swiftlint lint --quiet` (0.65.1) exits 0 with no new warnings in the changed parser or test files.
